# 为什么阈值是 20% 而不是 5%：本机**空闲时** util 就有 10~18%
#   —— 桌面合成器 + 常驻 Electron 窗口（WorkBuddy/豆包/WXWork/
#   DingTalk/B站，约 790 MiB）撑着。它们是图形进程，
#   nvidia-smi 的 compute-apps 里查不到，但让 utilization.gpu 常年有底噪。
#   而**真实计算负载时** util 稳定 95~100%。
#   所以 20% 恰好落在两者之间，是有效的分界。
#   （曾试「相对基线 baseline+8」，实测失败：采样里一次 0% 就把 min 基线
#     拉到 0，判据塌成 util<=8%，比不做还糟。）
#   第一版门控就是这么写的，三个配置各等 900s 然后全部 SKIP。
#
# 每配置 6 轮，batch=512，每轮记录 util 与显存。
# 事后按 util 分档：util<=20% 的轮次为「低档」，其 median 是可信值；
#   util>20% 的轮次为「高档」（被占用时的下界），单独列出。
#   （见文件末尾的分档统计）。
# 口径：只计 forward + synchronize，不含数据准备。
# 注意：被别的进程占着只会让数字偏慢，所以被占时的数据是下界不是上界。

【结论】可信值 = 低档轮次的中位数（GPU 安静时测得）：
  fp32    0.0274 ms/img =    423×  （低档 1 轮）；另有 5 轮高占用未计入
  fp16    0.0160 ms/img =    725×  （低档 2 轮）；另有 4 轮高占用未计入
  int8    0.0690 ms/img =    168×  ⚠️ **无低档轮**（6 轮全在高占用）
          ↑ 这是**被占用时的下界**，不是性能上限。机器空闲后重跑 `ROUNDS=6 bash idle_final.sh` 即可得到可信值。

口径说明：
  · 基线 ncnn CPU fp32 = 11.6 ms/img = 1×
  · median 是对外报数口径；min 是硬件能力上限
  · util 是每轮**开跑前**的采样值（那才是外部负载）；
    本进程自己的占用不计入——所以采到的就是别人在抢多少。
  · 被别的进程占着只会让数字偏慢，所以被占时的数据是下界不是上界
  · 高档轮不删除（是有效的「被占用时」参考），但**不计入主结论**
